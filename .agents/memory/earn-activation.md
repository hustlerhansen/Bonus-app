---
name: Earn activation discipline
description: Why feature delivery must not clear the separate authentication/security release gates.
---

Completing an earn implementation is not permission to clear the previous authentication/security gates or select a real administrator/partner. Keep the activation gate closed until the separately assigned security/login work is explicitly cleared. Browser verification must not temporarily activate the shared development gate; use isolated databases for settlement tests.

**Why:** The user's earn assignment explicitly depends on separate phase-1 gates that remained unresolved. Opening a shared gate merely to demonstrate the feature would bypass that prerequisite.

**How to apply:** Build and test the earn mechanics independently; distinguish implemented code from activated commercial capability. Use synthetic test identities for protected UI checks and restore temporary privileges afterward.

Historical liability correction is not release clearance. Do not require reopening new earning to correct an already approved award.

**Why:** An incident may require stopping new earning while an administrator still needs to undo historical credit. Treating a safety shutdown as a ban on corrective action would force unsafe reactivation.

**How to apply:** Keep correction permissions, ledger invariants and audit checks intact, and never interpret a successful reversal as permission to activate earning.
